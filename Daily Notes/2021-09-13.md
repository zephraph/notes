Adam:  

> What I see is that something like 95% of await calls happen instantaneously after the function call, and then 4% are a little bit fancy, and only 1% are really getting fancy.

The way they seemed to think of it was that “being async” is a property of the system as a whole, and there’s no real middle ground. So if you expect to run into that 1% of cases where performance really falls off, you need to make the whole system async, even if you immediately `await` your functions.

### Execution model

My guess based only on the meeting: similar to JS. Even if you await an async function, it’s still going to execute asynchronously, i.e., the executor is going to toss it on the queue of things to run, and if there’s anything else of immediately importance (it may or may not have any concept of priority) it can do that before running your thing. As Adam said, most of the time it’s going to get executed right away.  
The async Rust book’s [async/await primer](https://rust-lang.github.io/async-book/01_getting_started/04_async_await_primer.html) has me covered:  

> Unlike `block_on`, `.await` doesn’t block the current thread, but instead asynchronously waits for the future to complete, allowing other tasks to run if the future is currently unable to make progress.

And from the chapter on the Future trait:  

> Futures can be advanced by calling the `poll` function, which will drive the future as far towards completion as possible. If the future completes, it returns `Poll::Ready(result)`. If the future is not able to complete yet, it returns `Poll::Pending` and arranges for the `wake()` function to be called when the Future is ready to make more progress. When `wake()` is called, the executor driving the `Future` will call `poll` again so that the `Future` can make more progress.

Without `wake()`, the executor would have no way of knowing when a particular future could make progress, and would have to be constantly polling every future. With `wake()`, the executor knows exactly which futures are ready to be `poll`ed.  
So futures actually tell the executor when they’re available to be polled. This is actually the [main difference](https://blog.rust-lang.org/2019/11/07/Async-await-stable.html#zero-cost-futures) between Rust Futures and JS promises:  

> The other difference between Rust futures and futures in JS and C# is that they are based on a “poll” model, which makes them zero cost. In other languages, invoking an async function immediately creates a future and schedules it for execution: awaiting the future isn’t necessary for it to execute. But this implies some overhead for each future that is created.
